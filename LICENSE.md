# LICENSE TEMPLATE: GitLab License Approval Policies Guide

## Overview
This template provides guidance on implementing GitLab License Approval Policies according to GitLab Ultimate documentation. These policies help enforce license compliance by specifying criteria that determine when approval is required before a merge request can be merged.

**Tier:** GitLab Ultimate  
**Offering:** GitLab.com, GitLab Self-Managed, GitLab Dedicated

## Prerequisites

Before implementing license approval policies, ensure the following requirements are met:

### 1. Dependency Scanning Configuration
License approval policies rely on dependency scanning job output. Without proper configuration:
- Policies have no data to verify requirements
- By default, policies "fail closed" and assume merge requests contain vulnerabilities
- You can configure policies to "fail open" using the `fallback_behavior` property

### 2. Enable Dependency Scanning
Choose one of these approaches:
- Create a **scan execution policy** that enforces Dependency Scanning across all target projects
- Configure **dependency scanning** in each project's `.gitlab-ci.yml` file
- Enable through the **Security Configuration panel**

### 3. Supported Packages
License approval policies require license information from [GitLab-supported packages](https://docs.gitlab.com/user/compliance/license_scanning_of_cyclonedx_files/#supported-languages-and-package-managers).

## Implementation Steps

### Step 1: Link Security Policy Project
1. Link a security policy project to your development group, subgroup, or project
2. **Required Role:** Owner

### Step 2: Create License Approval Policy
1. Navigate to **Secure > Policies** in your project
2. Create a new **Merge Request Approval Policy**
3. In the policy rule, select **License scanning**

## License Approval Criteria

### Prohibited Licenses
Configure policies to require approval when:
- Any license from an explicitly prohibited list is detected
- Any license is detected except those explicitly listed as acceptable

### Comparison with Default Branch
Set criteria based on licenses in the default branch:
- **Denied licenses**: Require approval only if the license is part of a new dependency
- **Existing components**: Require approval if denied license exists in components already in default branch

## Policy Behavior

When a license violation is found:
- The merge request is **blocked**
- Developer is instructed to remove the violating license
- Merge cannot proceed unless:
  - The denied license is removed, OR
  - An eligible approver for the License Approval Policy approves the merge request

## Troubleshooting Common Issues

### License Compliance Widget Loading
Loading spinner appears when:
- Pipeline is in progress
- Pipeline complete but still parsing results
- License scanning job complete but pipeline still running

**Solution:** Widget polls every few seconds; final state shows when pipeline is complete and parsed.

### Unknown Licenses Blocking Merge Requests
This occurs when:
- Dependency scanning fails to identify a license
- New/uncommon licenses aren't recognized
- License information is missing/incomplete in component metadata

**Resolution Steps:**
1. Review the **Licenses tab** in pipeline page
2. Check `out-of-policy` licenses generated by GitLab Security Bot
3. Manually investigate components with `unknown` licenses
4. Remove or replace affected components if licenses are unacceptable

**Temporary Workaround:**
1. Edit license approval policy
2. Add `unknown` to allowed licenses list
3. **Important:** Remove `unknown` from allowed list after resolving issues

## Best Practices

### 1. Legal Team Consultation
- Always consult legal team for license compliance issues
- Especially important when handling `unknown` licenses

### 2. Policy Scope
- License approval policies apply to **protected target branches only**
- Ensure proper branch protection is configured

### 3. Regular Review
- Periodically review and update approved/denied license lists
- Monitor for new license types in dependencies
- Keep security policies aligned with organizational compliance requirements

## Template Variables for Implementation

Replace these placeholders when implementing:

- `[PROJECT_NAME]`: Your project name
- `[SECURITY_POLICY_PROJECT]`: Name of your linked security policy project
- `[APPROVED_LICENSES]`: List of organization-approved licenses (e.g., MIT, Apache-2.0, BSD-3-Clause)
- `[DENIED_LICENSES]`: List of prohibited licenses (e.g., GPL-3.0, AGPL-3.0)
- `[APPROVER_GROUPS]`: Groups authorized to approve license policy violations

## Example Policy Configuration

```yaml
# Example license approval policy
scan_execution_policy:
  type: scan_execution_policy
  rules:
    - scan_type: dependency_scanning
      fallback_behavior: fail_closed
      license_policy:
        approved_licenses:
          - MIT
          - Apache-2.0
          - BSD-3-Clause
        denied_licenses:
          - GPL-3.0
          - AGPL-3.0
```
